- **`mnemo dispatch` from a `bypassPermissions` session spawns its children again on Claude Code 2.1.321, on the lean profile.** The CLI now refuses a background child in bypass unless the launch reads your user settings, because that is where it keeps your acceptance of the bypass disclaimer. The lean profile left user settings out, so every dispatch from a bypass session failed with "Acceptance is kept in your user settings, which this launch does not read". A lean child of a bypass parent now reads your user settings (`--setting-sources user,project,local`). Its own settings file then switches off every plugin you enabled there; a plugin the repo itself enables stays on. It also gets your user skills, your hooks, and your default model and effort when the dispatch names none. Measured on one machine, its first turn costs about 4,100 tokens more than a lean `auto` child and 7,600 fewer than `--full-profile`, which was the only way through before. The dispatch report's `profile:` line says what such a child loads. If your user or managed settings do not record the acceptance (`skipDangerousModePermissionPrompt`), the child runs `auto` and the `mode:` line says why. If the CLI still refuses, the error names `dispatch.childMode: auto` and, when it would help, `--full-profile`. `mnemo resume` and the PR follow-up wake no longer wake a bypass child dispatched before this fix: Claude Code 2.1.321 wakes such a child in `default` mode, where it stops at its first prompt. They say so and leave it, and a new dispatch is the way on. `tools/measure_bypass_lean.py` measures all of this on throwaway sessions. (#822)
